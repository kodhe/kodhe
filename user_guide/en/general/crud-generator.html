CRUD Generator (make:crud)

php console make:crud <ResourceName> builds a complete CRUD set in a single
command — like php artisan make:* in modern frameworks. The generated output can
follow the style you choose:

  • Routing style: kodhe (modern router, Route::resource) and/or CI3 (legacy $route[...]) — via --style.
  • View engine: CI3-style native PHP (*.php) or Blade (*.blade.php) — via --engine.

Routes are registered automatically into the project's configuration files, so
there is no more manual editing after generating. Good for: quickly porting one entity
from a CI3 application, or building a new admin module (list → create → edit → show →
delete) in a Kodhe project.

1. Syntax

php console make:crud <ResourceName> [field:type ...] [options]
PartDescription
<ResourceName>Required. UpperCamelCase, singular form: Post, Article, ProductTag
field:typeOptional, many allowed. List of table + model columns. Example: title:string body:text published:bool
--style=kodhe|ci3|bothWhich route style is registered automatically (default: both). kodhe → app/Config/routes_modern.php, ci3 → app/Config/routes.php
--engine=php|bladeView engine of the generated files (default: php). blade produces *.blade.php resolved through the Kodhe ViewFactory
--forceOverwrite existing files (default: the generator stops and writes nothing at all when there is a conflict)
--path=Custom output location (global make:* option)

Equivalent invocation aliases: php console g:crud Post, php console generate crud Post.

Recognised field types

Written asBecomes a column (migration Forge)Notes
string (default)VARCHAR(255)Any mistyped name automatically falls back to string
textTEXT
integer / intINT(9)
boolean / boolTINYINT(1)
date / datetime / decimalas their names imply

The id column (auto-increment primary key) and created_at/updated_at
(DATETIME) are added automatically — do not redeclare them. Without a field list,
the generator uses the default example name:string.

2. Generated artefacts

Example: php console make:crud Article title:string slug:string body:text published:bool

FileContents
app/Models/Article.phpModel extending Kodhe\Framework\Database\Model (CI3-compatible ORM). $table = 'articles', $useTimestamps = true, and $allowedFields filled automatically from the field list (without id) so mass-assignment insert()/update() is immediately safe to use
app/Controllers/ArticleController.phpController extending Kodhe\Framework\Http\Controllers\BaseController with full actions: index create store show edit update delete. The class name gets the Controller suffix so it does not clash with the identically named Model
database/migrations/<timestamp>_create_articles_table.phpAnonymous-class migration with up()/down() using the modern database stack: Loader::dbforge(kodhe()->db, true) + add_field/add_key/create_table (not the legacy CI::load_dbutil)
app/Views/articles/index.phpListing table + Show/Edit/Delete buttons (.blade.php extension when --engine=blade)
app/Views/articles/create.phpAdd form (POSTs to the resource)
app/Views/articles/edit.phpEdit form (POSTs to update/{id})
app/Views/articles/show.phpDetail of a single record
app/Views/articles/_form.phpShared form fields — already filled automatically according to the field:type list you declared (<input>/<textarea>/<select> per column, complete with old values for edit mode)
app/Config/routes_modern.php (with --style=kodhe/both)Modern routes added automatically: Route::resource(...) + the POST update/{id} and DELETE {id} routes pointing at the generated controller methods
app/Config/routes.php (with --style=ci3/both)The CI3-style $route['articles/...'] map is added automatically (7 URI patterns: index/create/store/show/edit/update/delete)

Automatic naming: table = plural snake_case (ProductTag → product_tags),
URL segment = plural kebab-case (/product-tags). The pluralizer is still simple —
double-check table/URL names for irregular words (e.g. Category → categories is
correct, but foreign technical terms may be wrong) and adjust them if needed.

3. Automatic routes (--style) & view engine (--engine)

The generator registers routes directly according to the chosen style — no manual
editing anymore. Target files are created automatically when missing, and writing is
idempotent: every block is marked with a /* make:crud:<res> */ marker, so
re-running the same command does not produce duplicates (the output is simply `Routes
already present`).

--styleWritten toContent added
kodheapp/Config/routes_modern.phpRoute::resource('articles', 'App\Controllers\ArticleController', ['except' => ['destroy']]) + Route::post('/articles/update/{articles}', ...@update) + Route::delete('/articles/{articles}', ...@delete)
ci3app/Config/routes.php7 $route['articles...'] = 'article/<action>' patterns in legacy CI3 style
both (default)both files aboveboth at once

Technical notes:

  • Why except destroy + a manual DELETE route? The modern Route::resource calls a destroy() method, while the generated controller follows the CI3 convention delete(). The explicit DELETE route bridges the two without changing the kodhe/http router.
  • Update via POST. The CI3 router maps by URI (a single $route array, no method separation), so the legacy form is POST /articles/update/{id}. To stay consistent across both styles, the generated views always submit the edit form to /articles/update/{id} and the generator also registers Route::post(.../update/{id}) on the modern side. (The standard resource PUT /articles/{id} remains available if you want to use _method spoofing.)
  • Modern routing is active only when $config['enable_modern_routing'] = TRUE in the project configuration; routes_modern.php is loaded at that point.
  • Write actions (store/update/delete) accept POST; the delete button in the listing view is already a <form method="post"> so it matches these routes.

View engine

--engineResultWhen to use
php (default)app/Views/articles/*.php — native PHP/CI3 syntax (<?= base_url(...) ?>, htmlspecialchars())Pure CI3-style projects
bladeapp/Views/articles/*.blade.php — Blade directives ({{ }}, @foreach)Projects using the Kodhe ViewFactory (default engine: blade)

The generated controller automatically references view names with the correct extension
for the chosen --engine, so no further adjustment is needed.

Common combination examples:

# Old CI3 project -> routes.php only, native views
php console make:crud Post title:string body:text --style=ci3

# Modern Kodhe project -> routes_modern.php only, Blade views
php console make:crud Post title:string body:text --style=kodhe --engine=blade

# Default: register both routing styles, native views
php console make:crud Post title:string body:text

4. Complete workflow (real example)

# 1) Generate the whole stack (routes registered immediately, form pre-filled)
php console make:crud Article title:string slug:string body:text published:bool

# 2) Run the migration (via kodhe/migration)
php -r "require 'vendor/autoload.php';
$m = new Kodhe\Framework\Migration\Migration(['migrations_path' => __DIR__.'/database/migrations']);
$m->latest();"

# 3) Test — no manual editing step left
php console serve
# open http://localhost:8080/articles

5. Important notes

  • Validation & CSRF are not automatic yet. The store()/update() actions call $this->input->post(NULL, TRUE) and then insert() directly. For production, add $this->load->library('form_validation') (or the kodhe/validation package) in the controller, and enable CSRF as described in the security guide.
  • The migration stub uses modern components — Kodhe\Framework\Database\Loader::dbforge() rather than CI3 dbutil. The CI3-style ORM layer on the Model is kept for legacy compatibility; new code should target the refactored package API.
  • Do not regenerate subsequent changes. Once the generated CRUD files have been customised, regenerating with --force will overwrite your customisations — use separate make:model/make:controller commands for manual iterations.
  • The generator is atomic before writing: if any one of the 8 files already exists, no file is written (the error message names which file).
