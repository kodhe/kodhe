Migrating from CodeIgniter 3 to Kodhe Framework

This guide is the complete path for moving a CodeIgniter 3 application to
Kodhe Framework. The big principle: Kodhe is not a new framework you have to
learn from scratch — it is the CI3 libraries modernised into Composer packages under
the Kodhe\Framework\* namespace, wrapped in a compatibility-layer kernel so old CI3
code keeps running. You may migrate incrementally, module by module.

0. Strategy: two paths, mixing allowed

PathBest forHow
A. Compat layer (light big-bang)Large CI3 apps, want to run again quickly on PHP 8Install the framework/ kernel, run CI3 controllers/models as-is; the $CI->load->library() loader keeps working + automatic CI_* aliases
B. Pure packages (incremental)New code / gradual refactoringcomposer require kodhe/<package> then use the PSR-4 classes directly (use Kodhe\Framework\...) without the loader

Recommendation: start with A so the application comes back alive, then move modules
one by one to B. Both can run side by side in one application
(dual-mode loader — see architecture).

1. Prerequisites & auditing the legacy code

Audit first before touching composer:

# patterns that are dead in PHP 8
grep -rn "mysql_\|mcrypt_\|each(\|create_function" application/ | wc -l

# all CI3 library/loader usages that need mapping
grep -rn "\$this->load->library(" application/controllers application/core | sort

# legacy API calls (email, old DB session, etc.)
grep -rn "reply_to\|set_mailtype\|lastactivity" application/

Make sure the original CI3 application already runs on PHP 8.1+ with strict error
reporting — first fix the PHP-7-inherited deprecated warnings (undefined variables,
strlen(null), etc.) before adding the migration layer.

2. Installation

Details in installation. In short:

# Path A — full-stack application (kernel + all packages)
composer require kodhe/framework

# Path B — only the packages you use
composer require kodhe/validation kodhe/session kodhe/http

The CI3 application folder structure (application/config, controllers, models,
views, migrations) does not change — the kernel reads it as-is.

⚠️ But note: Kodhe also has its own structure conventions for new code —
PascalCase folders without underscores (app/Controllers/, app/Models/) and a dual
router system (modern + legacy) whose behaviour differs from CI3. This is a real issue
during incremental migration; the full mapping together with the coexistence strategy
is in Folder Structure & Router, and the
standard for writing each component (controller/model/library/view) with per-file
conversions is in Standard Application Components.

3. Bootstrapping the application

Replace the bootstrap in index.php. CI3:

// Original CI3
require_once '../application/vendor/codeigniter/core/CodeIgniter.php';

Kodhe (kernel mode):

require_once __DIR__ . '/vendor/autoload.php';

$app = Kodhe\Framework\Foundation\Application::create();
$app->bootstrap();   // boot the kernel: register services into the container
$app->run();         // handle request globals → send the response

Pure package mode needs no bootstrap at all — just
require 'vendor/autoload.php' and instantiate the classes you need
(see running.md § Pure package mode).

Application requires the kodhe/http package; if it is not installed you will get a
RuntimeException with the composer require kodhe/http instruction.

4. Configuration: CI3 arrays are accepted as-is

The kernel reads CI3-style configuration (config.php, database.php) and translates
it into the service container (framework/src/Config/Setup.php). You do NOT need to
rewrite the config files. What must be checked/changed:

CI3 keyStatus in Kodhe
base_url, index_page, uri_protocol✅ same
sess_driver, sess_cookie_name, sess_expiration✅ same; sess_save_path must be filled (table name for the database driver, folder for files)
$db['default'] (hostname, username, …)✅ same; mysqli/pdo drivers
encryption_key⚠️ only relevant for the old encrypt package; the modern encryption package uses its own key — see encrypt.md

5. Namespace & loader map

This is the heart of the migration. The full table of loader names → FQCNs → packages is
in the namespace migration map. The general pattern:

CI3 originalKodhe (new code)
CI_Session, $this->load->library('session')Kodhe\Framework\Session\Drivers\*
CI_Form_validationKodhe\Framework\Validation\FormValidation (package kodhe/validation)
CI_PaginationKodhe\Framework\Pagination\Pagination
CI_EmailKodhe\Framework\Email\Email
CI_UploadKodhe\Framework\Upload\Upload
CI_Image_libKodhe\Framework\Image\Image
$this->db->… (query builder)Kodhe\Framework\Database\*
Kodhe\Session\Session (legacy Kodhe)❌ obsolete — always use the Kodhe\Framework\ prefix

Rules of thumb:

  1. Old $this->load->library('x') code keeps running via the compat layer — don't touch it yet; let the loader resolve through packageMap.
  2. New code always uses use Kodhe\Framework\<Package>\<Class>; — never write CI_* or Kodhe\<Package> without Framework.
  3. After changing FQCNs: composer dump-autoload -o.

6. API changes to search for in your code

Some methods were normalised to camelCase and some config moved elsewhere. Check each
package's README (the source of truth for the API); the summary:

AreaCI3Kodhe
Email$this->email->reply_to(…), set_mailtype(…)replyTo(…); mailtype became a configuration option
DB sessionslastactivity columnmodern CI3 schema: timestamp (gc still supports the old column as a fallback) — DDL in troubleshooting §2
Migrationrequired the superobject $CInew Migration(['migrations_path' => APPPATH.'migrations']) — see migration.md
Encrypt/Encryptionone librarytwo separate packages: kodhe/encrypt (legacy) & kodhe/encryption (modern); decrypt old data with encrypt, re-store with encryption
Pagination$config + initialize()still compatible; a factory via the kodhe/http integration is also available

Every page in libraries/ has a per-package Migration notes
section — use them as a checklist when grepping and replacing.

7. Database, sessions, and support tables

  1. Create/fix the ci_sessions table according to the new schema (see troubleshooting §2), then make sure sess_save_path points to its name.
  2. The ci_migrations table is still used by the kodhe/migration package; old migration files (NNN_name.php containing a Migration_* class) **do not need to be changed**.
  3. The $this->db query builder in CI3 models runs on top of Kodhe\Framework\Database\* through the container — no syntax changes for standard usage (get, where, insert_batch, transactions).

8. Phased verification checklist

Run in order; every step must be green before moving on:

  • [ ] composer install without conflicts; composer dump-autoload -o
  • [ ] Static pages / default route render (kernel boots successfully)
  • [ ] Old CI3 controllers respond; check the logs: no Class "..." not found
  • [ ] Login/logout: session read-write OK (files driver first, then database)
  • [ ] Image upload + image resizing (requires gd/imagick)
  • [ ] Sending email over a test SMTP
  • [ ] form_validation on the hardest forms (custom callback rules)
  • [ ] Migration latest() / version() on a staging DB
  • [ ] Encryption: decrypt old data → re-encrypt → verify (see Encrypt::migrate() in Security §5)
  • [ ] CSRF: form POST with a valid token passes; a wrong token produces 403
  • [ ] Regression suite / manual end-to-end smoke tests
  • [ ] Final security audit: run the pre-production checklist in Security §10

The most common errors at this stage are already documented with their solutions in
troubleshooting.

9. Gradual consolidation into modern mode

For every module you touch after the initial migration:

  1. Replace $CI/$this->load access with explicit instantiation: ```php use Kodhe\Framework\Validation\FormValidation; $validation = new FormValidation(); $ok = $validation->run($post, 'login'); ```
  2. If kernel built-in helpers are used, consider HelperManager (framework/src/Support/Modern/HelperManager.php) for modern-style lazy-loaded helpers.
  3. Once an area is 100% in package mode, remove its kernel dependency — the application may eventually run without framework/ at all.

10. Rollback

Because Path A changes neither the application structure nor the config files, rollback
is as easy as restoring the original CI3 index.php bootstrap and removing the composer
dependencies. Data (sessions, old ciphertext, migration tables) is deliberately kept
two-way compatible for as long as possible — except for re-encrypted results from
kodhe/encryption (step 8), which only the modern package can read. Therefore perform
re-encryption only after the application is stable.
