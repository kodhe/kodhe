Services, Modules, Modern Routing & Facades

This page completes the documentation of the built-in Kodhe Framework features
(the framework/ kernel + the kodhe/http package) that are not covered elsewhere:
the service container & service providers (addons), the module system, modern routing
(Route::), middleware, and global facades. All APIs below are verified from the
source code: framework/src/Container, framework/src/Foundation/Service,
framework/src/Support/Modules.php, http/src/Routing, http/src/Middleware,
framework/src/Support/Facades.

For moving an existing application, see Migrating from CI3
and Folder Structure & Router.

1. Service Container (Kodhe\Framework\Container\Container)

The container is a dependency-injection registry with prefixed naming.
Every service is stored as a "prefix:Name" string; if no prefix is written, the
container automatically uses the native kodhe: prefix
(Container::NATIVE_PREFIX).

use Kodhe\Framework\Container\Container;

$c = new Container();

// new factory on every call
$c->register('mail:Mailer', function ($container, ...$args) {
    return new App\Services\Mailer(...$args);
});

// single instance (singleton)
$c->registerSingleton('app:Settings', function ($container) {
    return new App\Services\Settings(config_item('settings'));
});

$mailer = $c->make('mail:Mailer');          // RuntimeException if not registered
$c->has('mail:Mailer');                     // bool
$c->getBindings();                          // list of non-singleton bindings
$c->getSingletonBindings();                 // list of singletons
$c->replace('mail:Mailer', $obj);           // override an existing binding
$c->setThrowOnDuplicate(false);             // allow re-registering without an error

Implementation notes (as in the code):

  • make() is called variadically: extra arguments are forwarded to the closure/factory.
  • make() also accepts the form make($bindingObject, $name, ...$args) to resolve through a specific sub-binding.
  • Contract interface: BindingInterface (register, bind, registerSingleton, make); the ConcreteBinding decorator forwards to its delegate when a name is not found locally.
  • Not-found errors are thrown via Exceptions\ContainerException::notFound($id, $availableServices) (the message includes the list of available services).

2. ServiceProvider / ServiceLocator / ServiceManager (Addon system)

A set of classes in Kodhe\Framework\Foundation\Service for packaging features as
self-contained addons/modules (an ExpressionEngine-style inherited pattern):

ClassRole
ServiceLocatorProvider registry: register($prefix, $provider), has, get, all — duplicate prefix → Exception("Addon of name {$prefix} already registered.")
ServiceProviderBase class per addon; reads the array from the setup file, registers autoload namespaces, services, singletons, models, aliases
ServiceManagerOrchestration: scans the addon folder, addProvider(), collects data across providers (forward())
ServiceHelperStatic service access with automatic prefix detection

2.1 Addon setup file

An addon is a folder containing an addon.setup.php file that returns an array:

// addons/blog/addon.setup.php
return [
    'name'      => 'Blog',
    'version'   => '1.0.0',
    'author'    => 'Our Team',
    'namespace' => 'Addons\\Blog',            // registered with the Autoloader via addPrefix()
    'services'  => [                           // [name => Closure|string]
        'PostService' => function ($provider) {
            return new \Addons\Blog\PostService;
        },
        'TagService'  => 'Services\TagService', // string = FQCN relative to the addon namespace
    ],
    'services.singletons' => [
        'StatsService' => fn ($provider) => new StatsService(),
    ],
    'models' => [
        'Post',                                 // becomes Addons\Blog\Post
        '\Shared\Model',                        // leading backslash = do not namespace it
    ],
    'models.dependencies' => ['Post' => ['kodhe:db']],
    'aliases' => [
        'CI_Post' => 'Addons\\Blog\\Post',      // key = alias, value = real class
    ],
];

Rules enforced by the code (ServiceProvider::registerServices):

  • Service names must not contain : (it is used as the prefix separator).
  • Services are registered under the "{addon}:{Name}" key in the container; the provider's register/registerSingleton/make methods always force the prefix through ensurePrefix() (the special name App is mapped to kodhe:App).
  • A string value in services is wrapped with reflection: it instantiates the namespace\Class class with the remaining arguments.
  • Numeric-keyed aliases trigger a mapping of Kodhe\Modules... → the Modules... alias; for CI_* aliases the lowercase variant (CI_model) is registered too, so it is safe on case-sensitive Linux.

2.2 Runtime registration

use Kodhe\Framework\Support\Autoloader;
use Kodhe\Framework\Container\Container;
use Kodhe\Framework\Foundation\Service\{ServiceLocator, ServiceManager};

$container = new Container();
$locator   = new ServiceLocator($container);
$manager   = new ServiceManager($container, $locator);
$manager->setAutoloader(new Autoloader()); // required for registerNamespace

$manager->setupAddons(FCPATH . 'addons');  // scan folders that have addon.setup.php
// or manually:
$provider = $manager->addProvider(FCPATH . 'addons/blog'); // default prefix = folder basename

$manager->getPrefixes();     // ['blog', ...]
$manager->getNamespaces();   // ['blog:blog' => 'Addons\Blog', ...] (result of forward())
$manager->getModels();       // collected models keyed by '{prefix}:{name}'
$manager->setClassAliases(); // enable all 'aliases'

Prefix conflicts: an existing provider is never overwritten, unless the old path
contains Addons/pro/levelups or ExpressionEngine/Addons (pro/first-party priority —
internal logic of addProvider()).

2.3 Accessing services: ServiceHelper & the service() helper

use Kodhe\Framework\Foundation\Service\ServiceHelper;

ServiceHelper::get('email');                 // 'email' → EmailService (auto-suffix)
ServiceHelper::get('EmailService', 'blog');  // explicit prefix
ServiceHelper::email();                      // __callStatic: email() → EmailService
ServiceHelper::user_manager();               // snake_case → UserManagerService
ServiceHelper::getAvailableServices();       // list across all providers
ServiceHelper::clearCache();                 // reset cached instances & providers

// global function (framework/src/Support/Helpers.php):
$svc = service('email');            // delegates to ServiceHelper::get()
$svc = service('email', 'blog');

Name conversion (methodToServiceName): underscores are stripped then ucwords is
applied, and the Service suffix is appended when missing. Resolution uses
kodhe('App') (the Application/provider root instance) — which means **these helpers
only work once the Kodhe kernel/bootstrap is running**; in pure per-package mode, use
Container::make() directly.

3. Module System (Kodhe\Framework\Support\Modules)

A module = a self-contained application folder under APPPATH.'modules/' (other
locations are possible via the modules_locations config) with the CI3 HMVC-style
structure: controllers/ models/ views/ config/ (routes.php).

3.1 Lifecycle

  • Modules::init() — call once during bootstrap: determines the locations, tries the cache, then runs scanAndCacheAllModules(). The modern routers (Router, UnifiedRouter) call it automatically in their constructor.
  • Scan results are cached in a cache file (cache(), loadFromCache(), isCacheFresh($maxAge=3600), refreshCache(), clearCache()) — important in production because directory scanning is expensive.
  • Per-module routes are read from the module's own config/routes.php (parse_routes()), plus module route groups via Route::module().

Main API:

Modules::moduleExists('blog');           // bool
Modules::getAllCachedModules();          // [name => [path...]]
Modules::getFirstModulePath('blog');     // ?string
Modules::list_modules($excludeCore=false);
Modules::folders();                      // list of module locations
Modules::find($file, $module, 'config/'); // [path, file] HMVC convention search
Modules::run('blog/post/index', ...$args); // load controller + call method (ob capture)
Modules::load('blog/post');              // instantiate the module controller (registry)
Modules::controller_exists('post','blog');
Modules::path($module, $folder);         // module folder path
Modules::register_asset($asset); Modules::assets();

Modules::run() validates the argument count against the method's required parameters
(ReflectionMethod) and returns string/NULL output; failures are logged through
log_message('error', ...).

4. Modern Routing (Route:: from kodhe/http)

Beyond the CI3-style $route['uri'] = 'class/method', the kodhe/http package
provides a fluent router (Laravel-style) in
Kodhe\Framework\Http\Routing\Route + RouteCollection:

use Kodhe\Framework\Http\Routing\Route;

Route::get('posts', [PostController::class, 'index']);
Route::post('posts', [PostController::class, 'store'])->middleware('auth');
Route::match(['get','post'], 'login', LoginController::class);
Route::any('ping', fn () => response('pong'));

Route::group(['prefix' => 'admin', 'namespace' => 'App\\Controllers\\Admin',
              'middleware' => ['auth','role:admin']], function () {
    Route::resource('users', UserController::class);      // index/create/store/show/edit/update/destroy
    Route::apiResource('tags', TagController::class);     // JSON variant
    Route::module('blog', function () { /* routes inside the module */ });
});

Route::apiVersion('v1', fn () => Route::get('feed', FeedController::class));
Route::domain('acme.example.test', fn () => Route::get('dash', DashController::class));
Route::view('about', 'pages/about', ['title' => 'About']);
Route::redirect('/old', '/new', 301);
Route::fallback(fn () => throw new NotFoundError());

Route::pattern('id', '[0-9]+');                  // global constraint
$name = Route::url('users.show', ['id' => 5]);   // reverse URL by name
Route::getRoutes(); Route::clear();

Other supporting features available: dynamic($prefix, $controller)
(auto-routes to a controller), permanentRedirect, api() (alias for the
api/ prefix), wildcardDomain*, getCurrentApiVersion()/setApiVersion().
The route collection supports caching: RouteCollection::cache(),
loadFromCache(), isCacheFresh() — enable it through the router config
cache_routes (see folder-structure-and-routing).

Resource fluency: Route::resource(...)->only([...])->except([...]) via
ResourceRegistrar (only/except/names/parameters/middleware).

5. Middleware

The http/src/Middleware folder:

  • MiddlewareInterface — the process(Request $request, callable $next) contract (implement it according to that file).
  • MiddlewareRegistry — a registry of named middleware that can be referenced by string in ->middleware('auth') / group attributes.
  • MiddlewareGroup — a set of middleware (e.g. web, api).
  • CallableMiddleware — wraps a closure as a middleware.
  • RateLimiter — rate limiter (used by the throttle attribute on routes/APIs).

Registration usually happens through your application's Kernel/routing config;
middleware runs in the pipeline before ControllerExecutor calls the action.
Request/response lifecycle details: http.md →.

6. Global Facades & Application Helpers

Kodhe\Framework\Support\Facades\Facade is a singleton service locator that also
becomes the content of $GLOBALS['kodhe']:

$f = Facade::getInstance();
$f->set('load', $loader);          // component registration (dev may override; prod stays silent)
$f->get('router');                 // InvalidArgumentException when missing
$f->has('di');                     // bool
$f->register('myMacro', fn() => …);// custom method → $f->myMacro()
$f->remove('tmp'); $f->all();
Facade::reset();                   // clear the singleton (testing)
  • __call forwards to a loader method when one exists, then to registered callbacks.
  • There is an automatic deprecated map (blacklist → blockedlist) that emits E_USER_DEPRECATED in development environments.
  • The base Controller (http/src/Controllers/Controller.php) takes the facade from $GLOBALS['CI_APP']->getKernel() / $GLOBALS['CI_KERNEL'] when available, falling back to Facade::getInstance(); BaseController adds the string helper, the user_agent library, and theme (when the kodhe/view package is installed).

Other global helpers in framework/src/Support/Helpers.php:
session($key=null), resolve_path(), csrf_token()/csrf_field()/csrf_meta(),
active_module(), service(). The kodhe() / app() functions are provided by the
application kernel/bootstrap (see the Foundation/Service README); make sure your
application version defines them — in pure per-package mode neither exists automatically.

7. When to use which?

NeedUse
Internal DI within a single-repo applicationContainer::register/make with your own prefix
Plug-and-unplug feature packages (addon marketplace)addon.setup.php + ServiceManager::setupAddons()
Fetch an addon service from a controllerservice('name') / ServiceHelper::name()
Turn part of a large app into a self-contained packageModules (HMVC) + Route::module()
Modern APIs/endpointsRoute::get/group/resource/apiVersion + middleware
Keep old CI3 code running$CI->load->library() dual-mode (see loader-kernel.md)

Known issues

  • ServiceHelper depends on kodhe('App'); if the App facade/container has not been booted, resolution throws an error — it does not return a graceful null.
  • ServiceManager::addProvider() silently returns (void) when the setup file is missing (the throw is commented out in the code) — hard to debug; check the debug log.
  • setupAddons() only processes folders that contain addon.setup.php; addons without that file are skipped without a warning.
  • Prefix-conflict priority is hardcoded to the path strings Addons/pro/levelups / ExpressionEngine/Addons — an artefact of the EE origins; for new projects you should avoid duplicate prefixes.
  • getAvailableServices() on a provider relies on that provider's own getAvailableServices() method; the base ServiceProvider does not define it, so the default returns [] unless the addon implements it.
