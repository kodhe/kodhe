Kodhe Standard Application Components (Controllers, Models, Libraries, Views/Templates)

This page is the standard for writing application components in Kodhe Framework —
the correct folders, namespaces, and base classes — together with **how to migrate each
component from CodeIgniter 3**. For the overall migration strategy see
migrating-from-ci3; for folder structure & router differences see
folder-structure-and-routing.

Quick summary

ComponentKodhe standardLegacy CI3 supportCLI scaffold
Controllerapp/Controllers/*.php, namespace App\Controllers, extends Kodhe\Framework\Http\Controllers\BaseController$this->load still available via Controller + LegacyLoadermake:controller
Modelapp/Models/*.php, namespace App\Models, extends Kodhe\Framework\Database\ModelOld extends CI_Model keeps working as-ismake:model

All Kodhe folder names use a leading capital letter and no underscores
(Controllers, Models, Middleware) — the kernel autoloader tolerates case
differences, but pure PSR-4 package mode demands full compliance.

1. Controller

Kodhe standard

<?php
// app/Controllers/Home.php
declare(strict_types=1);

namespace App\Controllers;

use Kodhe\Framework\Http\Controllers\BaseController;

class Home extends BaseController
{
    public function index()
    {
        return view('home/index', ['title' => 'Home']);
    }

    public function detail($id = null)
    {
        $item = \App\Models\ItemModel::find($id);
        return view('home/detail', ['item' => $item]);
    }
}

Facts from the code (http/src/Controllers/):

  • Controller (the base class) prepares the application Facade, stores a reference to the legacy controller (__legacy_controller), and calls load->initialize() so that $this->load (CI3-style model/view/library/helper) **keeps working inside modern controllers**.
  • BaseController adds optional auto-loading (the string helper, the user_agent library, theme registration when the kodhe/view package is installed). Every failure is fail-soft (packages may be absent).
  • RESTController is also available as a base class for APIs.

Migration from CI3

CI3:

class Welcome extends CI_Controller {
    public function index() {
        $this->load->model('item_model');
        $data['items'] = $this->item_model->get_all();
        $this->load->view('welcome_message', $data);
    }
}

Conversion steps:

  1. Move the file into app/Controllers/ with a **PascalCase file name matching the class** (Welcome.php containing class Welcome).
  2. Add namespace App\Controllers; and `use Kodhe\Framework\Http\Controllers\BaseController;, replaceextends CI_Controller→extends BaseController`.
  3. Public method names stay the same — both the legacy and the modern router will find them. By default the modern router looks for Home/Index/Main/Welcome as the front page controller.
  4. $this->load->model()/view()/library()/helper() do not have to change in the first phase (they are mediated by LegacyLoader). Consolidate gradually:
    • models → direct App\Models\... instantiation / DI,
    • views → the view() helper,
    • libraries → new Kodhe\Framework\... (see §3).
  5. Register old routes to the new controllers if you use the modern router:
Route::get('welcome', [App\Controllers\Welcome::class, 'index']);

⚠️ Do not mix two controller namespaces in one file, and avoid underscores in class
names (item_model → ItemModel) to stay PSR-4 compliant.

2. Model

Kodhe standard

The modern model lives in the kodhe/database package: Kodhe\Framework\Database\Model
(inheriting ORM\LegacyModel) with declarative properties and a chainable query API.

<?php
// app/Models/ItemModel.php
declare(strict_types=1);

namespace App\Models;

use Kodhe\Framework\Database\Model;

class ItemModel extends Model
{
    protected $table          = 'items';
    protected $primaryKey     = 'id';
    protected $returnType     = 'object';      // or 'array'
    protected $allowedFields  = ['name', 'price', 'category_id'];
    protected $useTimestamps  = true;           // created_at / updated_at
    protected $useSoftDeletes = false;          // deleted_at
    protected $validationRules = [];            // kodhe/validation integration
}

Main API (verified from database/src/Model.php):

  • Query builder: `select() where() orWhere() whereIn() like() orderBy() limit() groupBy() having() join() leftJoin() rightJoin() inRandomOrder()`
  • Eager relations: with(['category'])
  • Execution: `all() findAll($limit,$offset) first() find($id) findOrFail($id) count() sum() avg() max() min() chunk($size, fn)`
  • Writes: `insert($data, $returnId) insertBatch() update($data, $where) updateBatch() delete($id) restore() forceDelete() truncate()`
  • Upserts: firstOrCreate() firstOrNew() updateOrCreate()
  • The table can be swapped at runtime: $model->table('items_archive')

Example usage in a controller:

$cheap = App\Models\ItemModel::where('price', '<', 100)->orderBy('name')->findAll(20);

Migration from CI3

CI3:

class Item_model extends CI_Model {
    public function get_all() {
        return $this->db->get('items')->result();
    }
}

Conversion map:

CI3Kodhe
class Item_model extends CI_Model (file item_model.php)class ItemModel extends Model (file app/Models/ItemModel.php)
$this->db->get('items')->result()$this->findAll() / ItemModel::all()
$this->db->where(...)->get(...)->row()$this->where(...)->first()
$this->db->get_where('items', ['id'=>$id])->row()$this->find($id)
$this->db->insert('items', $data)$this->insert($data) (requires allowedFields)
$this->db->update('items', $data, ['id'=>$id])$this->update($data, ['id' => $id])
$this->db->delete(...)$this->delete($id) / soft delete via useSoftDeletes

Notes:

  • Old models extends CI_Model keep running in the compat kernel — they do not all have to be converted at once. Convert model by model as you touch them.
  • Modern mass assignment is restricted by $allowedFields; empty means rejected. When converting, list your writable columns.
  • Timestamps & soft deletes replace the manual date('Y-m-d H:i:s') habit of CI3 — just enable the properties and make sure the columns exist in the table.

3. Library

Kodhe standard

Every CI3 library has become a Composer package under the namespace
Kodhe\Framework\<Package>\*. The canonical way to use them is direct instantiation
or through the service container — no more $this->load->library().

use Kodhe\Framework\Email\Email;

$email = new Email();
$email->from('a@b.c')->replyTo('a@b.c')->to('x@y.z')->subject('Hi')->message('...');
$email->send();

Compatible path: $this->load->library()

framework/src/Config/Loaders/LegacyLoader.php contains a map of CI3 library names →
modern classes, so old code keeps running untouched:

CI3 callClass loaded
$this->load->library('email')Kodhe\Framework\Email\Email
'session'Kodhe\Framework\Session\Session
'form_validation'Kodhe\Framework\Validation\Validation
'pagination'Kodhe\Framework\Pagination\Pagination
'user_agent' / 'agent'Kodhe\Framework\Agent\UserAgent
'cache' 'calendar' 'cart' 'encrypt' 'encryption' 'ftp' 'image_lib' 'table' 'typography' 'upload' 'zip' 'parser' etc.the respective Kodhe\Framework\... equivalent in each package

Requirement: the relevant package must be installed via Composer (`composer require
kodhe/email`, etc.) — the loader only maps names, it does not provide the code.
Application-specific custom libraries (application/libraries/Mylib.php) are loaded as
usual by the kernel loader (case-insensitive).

Phased recommendation

  1. Migration phase: let $this->load->library(...) keep running via LegacyLoader.
  2. Consolidation phase: switch to new Class() / inject via the container; drop the dependency on the superobject. Details in migrating-from-ci3 §9.

4. Views & Templates

Kodhe standard

The kodhe/view package provides a multi-engine ViewFactory with the global
view() helper (from view/src/helpers/template.php):

// render directly
view('home/index', ['title' => 'Hello']);

// with a layout — the 4th argument of view(), or a preceding set_layout() helper
view('home/index', $data, false, 'layouts/main');
set_layout('layouts/main');   // applies to subsequent view() calls

// return as a string
$html = view('emails/greeting', $data, true);

ViewFactory features (verified from view/src/):

  • Engines: PhpEngine, BladeEngine, TwigEngine — chosen automatically per file (.php/.blade.php/.twig) or explicitly: `render($view, $data, $return, $engine)`.
  • Layouts: layout($name) + set($key, $value) for global template data.
  • Themes: enabled via the theme_enabled config; theme paths are searched in APPPATH/themes then FCPATH/themes; theme views take priority over regular paths (ThemeManager, plus AssetManager for theme assets).
  • Device variants: VariantManager (mobile/tablet/desktop).
  • HMVC modules: the module_view() helper renders a module's views.

Minimum configuration:

// config/view.php (read by ViewFactory)
'theme_enabled' => false,
'views_path'    => APPPATH . 'Views',   // the old view folder still works

View folders: Kodhe uses APPPATH/Views (PascalCase, no _), but the kernel loader
still finds the old application/views — so **CI3 view files do not need to be
restructured in the early phase**; renaming to Views/ happens during consolidation.

Migration from CI3

CI3Kodhe
$this->load->view('page', $data)still works (loader), or view('page', $data)
$this->load->view('page', $data, TRUE)view('page', $data, true) returns a string
$this->load->vars($data) / pass-by-referenceViewFactory::set($key, $value) or the data array

No syntax changes are needed inside view files (CI3 HTML + <?php ?> is valid in
PhpEngine). What to check: $this-> calls inside CI3 views (such as
$this->security->xss_clean()) — replace them with modern package instantiation because
Kodhe views are not bound to the controller.

5. Middleware & Others (brief)

  • Middleware: app/Middleware/ (namespace App\Middleware), implement Kodhe\Framework\Http\Routing\Contracts\MiddlewareInterface — full guide in services-modules-routing.
  • Custom helpers: put them in app/Helpers/ (kernel) or load them via HelperManager; the CI3 pattern $this->load->helper('x') is still served by the loader.
  • Migrations & seeders: see libraries/migration.

6. Automatic scaffolding

The CLI commands (verified from framework/src/Console/Commands/MakeCommand.php) create
files directly in the standard Kodhe locations:

php kodhe make:controller Home        # -> app/Controllers/Home.php  (App\Controllers)
php kodhe make:model ItemModel        # -> app/Models/ItemModel.php  (App\Models)
php kodhe make:migration create_items # -> migrations folder
php kodhe make:middleware Auth        # -> app/Middleware/Auth.php   (App\Middleware)
php kodhe make:command sync_data      # -> app/Console/Commands      (App\Console\Commands)
php kodhe make:crud Article title:string body:text published:bool  # -> a complete CRUD set (see notes below)

Options: --force (overwrite existing files), --path=... (custom location).

make:crud generates 8 files at once: the Model (app/Models/),
a full resource Controller (app/Controllers/<Name>Controller.php), the
create_<table>_table migration (modern Loader::dbforge() stack), and 5 CI3-style
views in app/Views/<resource>/. Full guide (field types, routes, workflow):
generator-crud.

How to bootstrap bin/console, create custom commands, and migrate CI3 is_cli() cron
jobs — see cli-console.

For App\* to be autoloadable, register it in the project's composer.json:

"autoload": { "psr-4": { "App\\": "app/" } }

then run composer dump-autoload.
